# 検証観点チェックリスト

## 比較対象
- pattern-flat：Flat構成（ファイル種別ごと）
- pattern-feature：機能別構成（Feature-based）
- pattern-fsd：FSD（Feature-Sliced Design）

## 題材アプリ
ライブオークション（入札+自動延長：フル実装 / 投げ銭・コメント：スタブ）

## 評価スケール
5段階：理想 / 許容 / 注意 / 非推奨 / 禁忌

---

## 1. 機能境界の独立性
- [ ] 機能間の参照方向（入札機能がコメント機能の内部実装を知らずに動くか）
- [ ] 共有ロジックの置き場（「金額表示」など複数機能で共通するものの置き場で迷わないか）
- [ ] 機能の追加・削除のしやすさ（「投げ銭機能だけ一時停止」のような要件に対し変更範囲が局所化されるか）

## 2. リアルタイム更新ロジックの配置
- [ ] WebSocket（モック）接続の置き場（どの層に属すべきか構造上迷わないか）
- [ ] 状態の伝播経路（「入札が入った」イベントが複数箇所に伝わる経路が追いやすいか）
- [ ] 自動延長ロジックの配置（残り時間判定〜延長処理〜通知表示の一連の流れが構造から推測できるか）

## 3. 変更コスト（保守性）
- [ ] 新機能追加時の変更ファイル数（例：「視聴者ランキング」追加で何ファイルに触れるか）
- [ ] 既存機能修正時の影響範囲（入札の表示仕様変更が投げ銭・コメントに波及しないか）
- [ ] ファイル探索のしやすさ（「自動延長の判定ロジックはどこ？」が構造から推測できるか）

## 4. チーム開発適性
- [ ] 並行開発のしやすさ（機能ごとに担当を分けてもコンフリクトが起きにくいか）
- [ ] オンボーディングコスト（新メンバーが構造を理解するまでの説明コスト）
- [ ] レビューのしやすさ（PRの差分が「何の機能か」を構造から判断できるか）

## 5. Next.js App Routerとの整合性
- [ ] ルーティングとの対応（app/ディレクトリとの構造の噛み合い）
- [ ] Server/Client Componentsの境界（分離が構造上自然か）
- [ ] co-locationとの相性（loading.tsx等との衝突がないか）

## 6. レンダリング方針の表現力（軽量版）
- [ ] 各機能の前提レンダリング方針（CSR/SSR）をコメントとして自然に書ける場所があるか
- [ ] 機能ごとの方針差を構造が暗示できるか

※ レンダリング戦略の本格比較は別軸（Pattern A）で後日実施
